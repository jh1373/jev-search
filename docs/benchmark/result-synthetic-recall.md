# 合成コーパスによる候補段の測定（結果）

状態: **測定済み**。ただし**合成データであり、実Vaultや一般的な日本語性能の主張には使わない。**
[プロトコルv1](protocol.md)のpilot/releaseとは別の、RV-02の切り分けを目的とした診断である。

## 目的

RV-02「BM25の候補漏れをJevでは救えない」を、Jevへの投資を増やす前に定量化する。

Jevは**候補に入ったものしか再ランキングできない**。したがって候補段の取りこぼし率が、
そのままJevを含めた製品全体の上限になる。ここを測らずに再ランキングを改善しても、
取りこぼした正解は永久に戻らない。

## 手法

- 生成器: `scripts/gen-corpus.mjs`（seed固定・決定的）。同一seedから同一バイト列を再生成できる。
- 測定器: `scripts/measure-recall.mjs`。**出荷する `src/core/search.ts` を直接import**する。
  再実装ではなく、実際に出荷されるコードを測る。
- 主題24件。各主題に2種類の正解ノートを用意する。
  - grade 2: 事実を述べる規程ノート（`規程/<主題>.md`）
  - grade 1: 同じ主題だが事実を述べない議事録（`議事録/<主題>-検討.md`）
- クエリは各主題2種。**この2種の差が本測定の中心である。**
  - `literal`: ノートの語彙をそのまま使う
  - `synonym`: **ノートの語彙を意図的に避けた**言い換え
- ノイズ: 主題の語彙を共有するが別の話題である distractor に加え、
  日記・レシピ・作業ログ・読書メモ・長文メモ（1200点で分割される規模）を混ぜる。
- 除外ポリシーは適用していない（合成Vaultに `Templates` / `Attachments` が無いため）。
- Recall@50 = 上位50チャンクに正解ノートが含まれる割合（プロトコルv1の定義に合わせた）。

## 結果

seed `20260919`。corpus hashは 400ノートが `175540f7da4cccd4`、10,000ノートが `fbe05e845a31bb2f`（先頭16桁）。

| 指標 | 400ノート | 10,000ノート |
|---|---|---|
| 索引構築 | 281 ms | 7,147 ms |
| クエリ数 | 48 | 48 |
| **Recall@5（全体）** | 62.5% | 60.4% |
| **Recall@10（全体）** | 68.8% | 64.6% |
| **Recall@50（全体）** | 79.2% | **68.8%** |
| MRR（全体） | 0.577 | 0.574 |
| **Recall@50（literal）** | **100.0%** | **91.7%** |
| **Recall@50（synonym）** | **58.3%** | **45.8%** |
| MRR（literal） | 0.899 | 0.889 |
| MRR（synonym） | 0.255 | 0.259 |
| 中央順位（literal / synonym） | 1 / 8 | 1 / 2 |
| 上位50件に入らなかった問 | 10 / 48 | **15 / 48** |

## 解釈

1. **語彙が一致すれば候補段はほぼ完璧。** literal の Recall@50 は400ノートで100%、10,000ノートでも91.7%。
   BM25 は「書いた言葉で探す」用途では十分に機能している。
2. **語彙が一致しなければ半分以上を取りこぼす。** synonym の Recall@50 は58.3% / 45.8%。
   つまり**Jevを足しても改善できない問が、全問の41.7%〜54.2%ある**。
3. **規模が増すと悪化する。** literal は100%→91.7%、synonym は58.3%→45.8%へ低下した。
   ノートが増えるほど distractor が上位を占め、正解が50位の外へ押し出される。
   「情報量が増えてもノイズが少ない」という性質は、**現状の候補段には無い**。
4. 1問は**BM25の一致が0件**だった（`パソコンの調子が悪いとき誰に言えばいい`）。
   語彙の重なりが完全に無い問では、候補段は空を返す。
5. MRR は literal 0.89 に対し synonym 0.26。**順位の質も語彙一致に強く依存する。**

## 限界（この結果をどこまで主張できるか）

- **合成データである。** 実際のVaultの語彙分布・表記ゆれ・同義語の使われ方を再現していない。
- **synonymクエリは意図的に厳しく作った。** ノートの語彙を避けるよう設計しており、
  実利用者の検索語がここまで離れているとは限らない。**最悪ケースの測定であって期待値ではない。**
- 主題24件・48問は統計的な結論を出すには少ない。信頼区間も出していない。
- 生成器の作者と評価者が同一である。プロトコルv1が求める独立判定を満たさない。
- したがって**「日本語検索のRecallは45.8%である」とは主張しない。**
  主張できるのは「**語彙一致に依存する候補段では、語彙が離れた問を取りこぼす。その率は規模とともに増える**」という機構である。

## この結果が設計に与える影響

- **ADR-005（BM25先行）は維持する。** 語彙一致の用途では十分に機能しており、置き換えの根拠はない。
- ただし**RV-02の優先度は上がる**。Jev再ランキングの改善は、候補に入った問にしか効かない。
  候補生成の改善（タイトル/aliases、同義語展開、候補多様化、ローカル埋め込み）を
  **Jevの品質測定より先に**比較する価値がある。
- G3（品質検証）でJevの改善を主張する場合、**候補段の上限を併記**する。
  「JevでnDCGが上がった」は候補に入った問の話であり、製品全体の改善ではない。

## 再現方法

```powershell
node scripts/gen-corpus.mjs --out=.sandbox/corpus-10k/vault --notes=10000 --seed=20260919 --clean
node scripts/measure-recall.mjs --vault=.sandbox/corpus-10k/vault --truth=.sandbox/corpus-10k/ground-truth.json --out=.sandbox/corpus-10k/recall.json
```

生成器は決定的なので、同じ `--seed` と `--notes` からは同じ corpus hash が出る。
`.sandbox/` は `.gitignore` 済みで、生成物はリポジトリに入らない。

## 次の手順

   合成データの数字を実文書へ外挿しない。
3. 候補段を改善した後に、Jev前後のnDCGを測る（G3）。
