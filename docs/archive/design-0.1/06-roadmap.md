## 3. ADR(Architecture Decision Records)

### ADR-001: BYOK(ユーザーの API キー)
- 状況: キーを開発者が集約するとコスト・規約・漏洩の全リスクを負う
- 決定: キーはユーザーが取得し設定画面で入力。コード・CI に埋め込まない
- 影響: 初回セットアップの摩擦と引き換えに、依存・課金責務が明確に分離

### ADR-002: Jev 機能の既定状態
- 状況: 「既定 OFF(最安全)」か「キー設定済みなら ON」か
- 決定: **キー設定済みなら ON・プレビュー既定 ON**。キーがなければローカル検索のみ
- 理由: プレビューがあるため初回送信は必ず可視化され、摩擦を最小化しつつ同意を担保

### ADR-003: モデルピン留め
- 決定: 既定 `jev-1.13.0`。docs の警告(レート制限等が動的)と、閾値再現性のため
- 変更時: 設定 UI で選択可能。ただし既定は固定

### ADR-004: ゼロ実行時依存
- 決定: ランタイム npm パッケージを導入しない(BM25・トークナイザ・キャッシュ自作)
- 理由: 供給網リスク・コミュニティ審査・バンドルサイズ。devDependencies は許可

### ADR-005: CJK bigram トークナイザ
- 決定: 外部形態素解析器を使わず、ASCII 単語+CJK bigram の混合
- トレードオフ: 精度は形態素解析に劣るが、ゼロ依存・十分な recall・実装が小さい

### ADR-006: 判定は Score 3 段階
- 決定: Noul 単独でなく 3 段階 Score(off-topic/related/answers)を採用
- 理由: metalmind の実装・運用知見、「related と answers の区別」が UI で価値になる

### ADR-007: 送信プレビューを既定 ON
- 決定: プレビュー同意をフローに組み込む(セッション単位で省略可)
- 理由: 一般ユーザーの最大心理的障壁(外部送信)への正面回答

### ADR-008: ベンチマーク同梱
- 決定: 日本語ベンチマークを製品に同梱し README で公開
- 理由: 先駆者が未開拓の差別化領域。悪い結果も含めて公開する

## 4. リスク登録簿

| ID | リスク | 影響 | 発生確率 | 対策 |
|----|--------|------|----------|------|
| R1 | Jev 価格が早期割引→恒久レート化で高騰 | ユーザー離脱 | 低〜中 | 使用量表示・キャッシュ・fetchK 調整・ローカル単体でも成立(P1) |
| R2 | レート制限の動的変更(公式警告済み) | 判定頻度低下 | 中 | バックオフ+フォールバック+キャッシュ |
| R3 | 日本語精度が BM25 と同等以下 | 差別化消失 | 不明 | **MS4 を最優先で実施**、悪結果も公開して信頼を得る |
| R4 | モデル更新で閾値が無効化 | 判定品質低下 | 中 | ピン留め(ADR-003)+README で閾値再調整手順 |
| R5 | コミュニティ審査不合格 | 配布遅延 | 低〜中 | テレメトリなし・同意フロー・デスクトップ限定の明示 |
| R6 | キーの平文保存が批判される | 信頼低下 | 中 | README 注意喚起+将来の OS キーストア対応を ADR で追跡 |
| R7 | TypeSafe 社の提供変更/終了 | 機能停止 | 低 | クライアント抽象化・ローカル機能は無傷(P1) |
